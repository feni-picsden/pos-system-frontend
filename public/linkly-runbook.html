Linkly EFTPOS — Complete Manual Test Runbook

For: operator-run testing on sandbox + Virtual PIN Pad (VPP) before Linkly/client acceptance and production credentials.

Format: every test tells you ① what to do on the WEBSITE, ② exactly what to do on the VPP (every keypress, or "do nothing" with the reason), ③ the EXPECTED OUTPUT. Tick ✅/❌ and note the log reference as you go.

Date: 28-Jul-2026 · covers all fixes committed 28-Jul (frontend 0cb8e1b, backend 6a68976).

THE CARD STEPS — the only card process you need, referenced in every test:

Swipe Card → choose CRD → enter PIN 1234 → press OK.

When a test says "CARD STEPS", do exactly that. When it says "do nothing", touch nothing on the VPP — the test explains why. Anything else (press CANCEL, wait 60s, do it twice) is spelled out.

0. Before you start (do once)

Testing runs on the DEPLOYED app — backend live on Vercel. No tunnel/ngrok needed: the Vercel URL is already public HTTPS, so Linkly webhooks reach it directly.

Server (Vercel — set once in the Vercel project → Settings → Environment Variables, then Redeploy):

  1. LINKLY_ENV=sandbox · LINKLY_POS_VENDOR_ID · LINKLY_WEBHOOK_SECRET · LINKLY_SECRET_ENC_KEY · LINKLY_DEFAULT_TERMINAL (if used) · DATABASE_URL = live Postgres.
  2. PUBLIC_BASE_URL=http://localhost:5000 — this is where Linkly posts notifications. No ngrok.
  3. Backend repo pushed (latest = the 28-Jul fixes) → Vercel auto-deploys. Confirm the deployment shows the latest commit.
  4. Live Postgres has the linkly_* tables — if not: from local, point DATABASE_URL at the live DB and run npx prisma db push (never migrate deploy on this DB).
  5. Evidence log: Vercel dashboard → project → Logs (Runtime), filter/search linkly — every request/response logs a JSON line with "scope":"linkly". Keep this open during all tests.

Website (deployed frontend):

  1. Frontend build must point at the live API: build with VITE_API_URL=http://localhost:5000/api (apiClient now reads it; falls back to localhost for dev) and deploy the 28-Jul build.
  2. Open the deployed site, log in as an admin user (needs register.manage), open a register on the sell screen.

VPP

  1. Start the Virtual PIN Pad, make sure it is paired (Setup → Linkly EFTPOS shows the green "Paired" chip).
  2. Auto Approve mode: after every VPP restart, Auto Approve is ON (transactions may approve without the PIN). For all the cent-value tests (sections 4, 5) you MUST turn it OFF: on the VPP press FUNC 7410 OK, then 1, then CLEAR, CLEAR, CANCEL. Each section below says which mode it needs.
  3. Cent-value simulation table (only works with Auto Approve OFF):
Sale total ends inVPP simulates
.00Approved (00)
.08Signature required (approves 08 after Yes on the website)
.50System error / declined (50)
.51Bank decline — CONTACT YOUR BANK (51)
  1. Doing nothing on the pad for ~60s = OPERATOR TIMEOUT (TM) — that is itself one of the tests.

1. Setup & pairing

T-1.1 Settings page loads

  • WEBSITE: Sidebar → Setup → Linkly EFTPOS.
  • VPP: do nothing — this is only a page-load check, no transaction is sent.
  • EXPECTED: page renders with "Paired" chip, Pair form, "Refresh status", "Logon" button. No console errors.

T-1.2 Logon (connection test)

  • WEBSITE: on Linkly EFTPOS page press Logon.
  • VPP: do nothing — the logon runs by itself; just watch the pad screen flash the logon and return to idle. No card, no keys.
  • EXPECTED: success message with response 00; backend log logon lines; pad idle again after.

T-1.3 Token cache

  • WEBSITE: run two purchases within an hour (e.g. T-3.1 twice).
  • VPP: CARD STEPS, twice — once for each purchase.
  • EXPECTED: log shows token.refreshed only ONCE (before the first txn); the second reuses the cached token.

T-1.4 Pairing rejected message (fix 28-Jul)

  • WEBSITE: simulate a dead secret: re-pair the VPP from another install OR temporarily corrupt linkly_pinpads.secret_cipher in the DB. Then attempt any purchase.
  • VPP: do nothing — the purchase is rejected before it ever reaches the pad; the pad stays idle the whole time.
  • EXPECTED: dialog error reads "PIN pad pairing rejected by Linkly — re-pair this terminal in Setup > Linkly EFTPOS." — not a generic failure. Re-pair afterwards and confirm a purchase works again.

2. Payment method configuration

T-2.1 Type dropdown (fix 28-Jul)

  • WEBSITE: Setup → Payment Methods → New → open the Type dropdown.
  • VPP: do nothing — settings page only, no transaction.
  • EXPECTED: groups Standard / Integrations / External. Integrations shows Linkly and Tyro only — "Linkly Value Added Applications" is hidden.

T-2.2 Method options persist

  • WEBSITE: Edit EFTPOS → change all options (4 colours incl. dark mode, Always Open Cash Drawer, Always Print Receipt, Use Rounding, Default to Pay Exact, Allow Cash Out) → Save → reopen.
  • VPP: do nothing — settings only.
  • EXPECTED: every option persisted exactly.

T-2.3 Always Print Receipt enforced (fix 28-Jul)

  • WEBSITE: set Always Print Receipt = ON for EFTPOS. Sell an item, pay by EFTPOS.
  • VPP: CARD STEPS.
  • EXPECTED: after the sale completes, the print window opens by itself (no Print click). Turn the flag OFF → next sale does NOT auto-print.

T-2.4 Outage fallback — standalone EFTPOS (fix 28-Jul, HIGH)

  • WEBSITE: Edit method "EFTPOS" → change Type: Linkly → EFTPOS (plain) → Save. Sell an item → Finalize → press EFTPOS.
  • VPP: do nothing — and watch that the pad NEVER wakes up. The whole point of this test: the pad must not be involved. If the pad shows PRESENT CARD, the test FAILED.
  • EXPECTED: payment records directly, no PIN pad dialog, sale completes. (Documented Linkly-outage procedure.) Change Type back to Linkly → next sale opens the PIN pad dialog again.

T-2.5 Tidy duplicate method

  • WEBSITE: Payment Methods list — delete the stray duplicate "EFTPOS CASH OUT" row (keep "EFTPOS Cash Out").
  • VPP: do nothing — settings only.
  • EXPECTED: list matches reference: Cash, Cheque, Direct Deposit, EFTPOS, EFTPOS Cash Out, Gift Card, …

3. Purchases — approved (any Auto Approve mode; amounts ending .00 if OFF)

T-3.1 Purchase via Finalize

  • WEBSITE: add product → Finalize → press EFTPOS (no amount typed = full balance).
  • VPP: CARD STEPS. (With Auto Approve ON the pad may approve by itself before you finish — that also counts.)
  • EXPECTED: dialog shows live pad screen ("PRESENT CARD" → "PROCESSING") → green Approved; payment recorded ONCE; sale auto-completes; customer + merchant copies visible in the dialog.

T-3.2 Purchase via sale key

  • WEBSITE: add product → press the EFTPOS sale key directly on the sell screen.
  • VPP: CARD STEPS.
  • EXPECTED: same as T-3.1; payment appears with card type + auth code in its description.

T-3.3 EFTPOS slip on the sale receipt — sale-key path (fix 28-Jul)

  • WEBSITE: after T-3.2 completes, print/preview the sale receipt.
  • VPP: do nothing — you are only checking the receipt from the previous test.
  • EXPECTED: the Linkly customer copy text appears on the sale receipt (this path used to drop it). Repeat for T-3.1's receipt (regression: still there).

T-3.4 Clear/Cancel blocked with card payment

  • WEBSITE: start a sale, take an EFTPOS payment, do NOT complete (leave balance) → press Clear Sale, then Cancel Sale key.
  • VPP: CARD STEPS for the payment first. Then do nothing — the clear/cancel attempts never touch the pad.
  • EXPECTED: both blocked with alert "Sales that contain integrated payments … cannot be cleared/cancelled without first refunding…".

T-3.5 Amount edges

  • WEBSITE: purchases of $0.01 and $1,234.00.
  • VPP: CARD STEPS, twice (once per purchase).
  • EXPECTED: pad shows the exact amount (cents map 1:1); receipts and payment rows match to the cent.

4. Declines, errors, cancels — turn Auto Approve OFF first (FUNC 7410 OK, 1, CLEAR, CLEAR, CANCEL)

T-4.1 Bank decline

  • WEBSITE: sale totalling $1.51 → EFTPOS.
  • VPP: CARD STEPS — the decline comes from the .51 amount, not from anything you press.
  • EXPECTED: red Declined, "CONTACT YOUR BANK" (code 51); no payment recorded; finalize stays open; pressing EFTPOS again starts a fresh attempt (new TxnRef).

T-4.2 System error

  • WEBSITE: sale totalling $1.50 → EFTPOS.
  • VPP: CARD STEPS — the .50 amount triggers the system error.
  • EXPECTED: declined with code 50 SYSTEM ERROR; no payment recorded.

T-4.3 Operator timeout

  • WEBSITE: start an EFTPOS payment, then just wait.
  • VPP: do nothing at all for ~60 seconds — do not swipe, do not press anything. The waiting IS the test.
  • EXPECTED: TM / OPERATOR TIMEOUT decline; no payment; dialog dismissable.

T-4.4 Cancel from the POS

  • WEBSITE: start an EFTPOS payment → press Cancel transaction in the dialog while the pad is waiting.
  • VPP: do nothing — do not swipe. Just watch: the pad should abort by itself right after you press Cancel on the website.
  • EXPECTED: log shows sendkey with Key "0"; txn ends declined/failed, never approved; no payment.

T-4.5 Cancel on the pad

  • WEBSITE: start an EFTPOS payment, then touch nothing on the website.
  • VPP: press the CANCEL key on the pad (do NOT swipe first).
  • EXPECTED: same as T-4.4 — declined/failed, no payment.

5. Signature flow — Auto Approve OFF

T-5.1 Signature — approve (fix 28-Jul: slip visible before Yes)

  • WEBSITE: sale totalling $1.08 → EFTPOS. When the Yes/No buttons appear: first check the "Merchant copy (signature slip)" box is visible in the dialog (print it if the customer must sign paper). Then press Yes.
  • VPP: CARD STEPS — then the pad shows PLEASE SIGN RECEIPT. Stop there, do nothing more on the pad. The answer is given on the WEBSITE (Yes button), not on the pad.
  • EXPECTED: slip visible before Yes; after Yes → Approved (08); payment recorded.
  • Note: Yes/No buttons come from webhook display events — if they never appear, fix the tunnel first (section 9).

T-5.2 Signature — decline

  • WEBSITE: repeat with $1.08 but press No.
  • VPP: CARD STEPS, then stop at PLEASE SIGN RECEIPT — do nothing more on the pad.
  • EXPECTED: Declined; no payment recorded.

6. Cash out (Auto Approve either; use .00 totals if OFF)

T-6.1 Cash out with a sale

  • WEBSITE: add product → EFTPOS Cash Out method → cash-out dialog → enter $20 → confirm.
  • VPP: CARD STEPS, once — it is ONE combined transaction (goods + cash), not two.
  • EXPECTED: one txn = goods + $20 (AmtPurchase + AmtCash); alert "Give the customer $20.00 cash out."; sale shows full card charge + Cash (Change) −$20 row.

T-6.2 Cash out without a sale

  • WEBSITE: empty cart → press Pay Exact Amount on the cash-out-enabled method → enter cash amount.
  • VPP: CARD STEPS.
  • EXPECTED: pad runs a CASH (TxnType C) transaction; approved; hand-over alert; recorded correctly.

T-6.3 "Allow cash out without sale" OFF (fix 28-Jul)

  • WEBSITE: Setup → General Settings → Allow cash out without sale = OFF → repeat T-6.2.
  • VPP: do nothing — the pad must never wake up. If PRESENT CARD appears, the test failed.
  • EXPECTED: blocked with "Cash out without a sale is disabled in General Settings." With goods in the cart, cash-out still works. Turn the setting back ON.

T-6.4 "No Cash Out" button

  • WEBSITE: in the cash-out dialog press No Cash Out.
  • VPP: CARD STEPS.
  • EXPECTED: card charged for goods only.

7. Split payments & terminal lock

T-7.1 Cash + EFTPOS split

  • WEBSITE: $30 sale → $10 Cash → then EFTPOS for the rest.
  • VPP: CARD STEPS, once — only the EFTPOS part reaches the pad; the cash part never does.
  • EXPECTED: card charged $20 only; sale completes; both payments on the receipt.

T-7.2 Card + card split

  • WEBSITE: split one sale across two EFTPOS tenders (type an amount first, then EFTPOS; repeat for the balance).
  • VPP: CARD STEPS, twice — once per tender, one after the other.
  • EXPECTED: two separate txns with two TxnRefs; both listed.

T-7.3 Split then decline (Auto Approve OFF)

  • WEBSITE: first tender any .00 amount, second tender ending .51.
  • VPP: CARD STEPS, twice — the second declines because of the .51 amount.
  • EXPECTED: first stays recorded; second declined; balance stays open; retry possible.

T-7.4 Terminal busy lock (fix 28-Jul)

  • WEBSITE: start an EFTPOS purchase and let the pad sit waiting (don't swipe yet). In a second browser tab, start another EFTPOS purchase (or press EFTPOS Settlement in Close Register).
  • VPP: do nothing while you fire the second attempt — the pad keeps showing the FIRST transaction only. Then finish the first one with CARD STEPS.
  • EXPECTED: second attempt fails fast with "Terminal is busy with another transaction …" (HTTP 409); the pad never sees it; the first txn completes normally.

T-7.5 Duplicate TxnRef guard

  • WEBSITE/TERMINAL: replay a purchase request with the same TxnRef via curl (run twice):

curl -X POST http://localhost:5000/api/linkly/purchase -H "Authorization: Bearer <JWT>" -H "Content-Type: application/json" -d '{"amountCents":100,"txnRef":"<SAME-REF>"}'

  • VPP: CARD STEPS for the first request only. The second request is rejected before the pad — the pad shows nothing new.
  • EXPECTED: second call → HTTP 409 DUPLICATE_TXNREF + the existing transaction row; no second charge.

8. Partial approval (fix 28-Jul)

T-8.1 Simulated partial approval

  • WEBSITE: start a $50.00 EFTPOS purchase; note the sessionId from the log.
  • VPP: do nothing — do NOT swipe. The "bank result" is faked by the curl below. (After the test, press CANCEL on the pad once to clear the leftover PRESENT CARD screen.)
  • TERMINAL: deliver the fake partial-approval result:

curl -X POST "http://localhost:5000/api/linkly/notify/<sessionId>/transaction" -H "Authorization: Bearer <LINKLY_WEBHOOK_SECRET>" -H "Content-Type: application/json" -d '{"ResponseType":"transaction","Response":{"Success":true,"ResponseCode":"00","AmtPurchase":2500,"AmtCash":0,"CardType":"VISA"}}'

  • EXPECTED: dialog approves; alert "Card approved $25.00 of $50.00 — take the remaining balance with another tender."; payment recorded $25.00; balance stays open; sale does NOT auto-complete.

9. Webhooks & recovery

T-9.1 Webhook delivery (live)

  • WEBSITE: with the tunnel up, run a normal purchase.
  • VPP: CARD STEPS.
  • EXPECTED: backend log shows notify.applied for display/receipt/transaction events; the pad screen mirrors into the dialog within ~2s.

T-9.2 Webhook auth reject

  • TERMINAL: curl -X POST "http://localhost:5000/api/linkly/notify/any-session/display" -H "Authorization: Bearer WRONG" -H "Content-Type: application/json" -d '{}'
  • VPP: do nothing — curl-only test, no transaction.
  • EXPECTED: HTTP 401; log notify.rejected_auth; no state change.

T-9.3 Idempotent notifications

  • TERMINAL: re-send T-8.1's exact curl a second time.
  • VPP: do nothing — curl-only test.
  • EXPECTED: first response applied, second duplicate; txn unchanged; exactly one event row.

T-9.4 Poll-only degradation — on the deployed setup this runs automatically

  • On Vercel there is no tunnel to kill; webhooks either arrive or the poll/auto-reconcile fallback carries the result anyway. This path was proven locally 27-Jul (every VPP pass resolved via poll while the tunnel was down).
  • Optional deliberate re-run: temporarily set Vercel env PUBLIC_BASE_URL to a dead URL → Redeploy → run one purchase (CARD STEPS) → dialog must still resolve Approved via polling → restore the env + Redeploy.

T-9.5 Timeout → Needs review → Check again

  • Only reachable when webhooks are NOT arriving (otherwise results land instantly). Run it during the optional T-9.4 dead-webhook window, or accept the 27-Jul local pass.
  • WEBSITE: start a purchase; let the dialog run past its 120s budget, THEN complete the card.
  • VPP: wait ~2 minutes doing nothing, then CARD STEPS (approve late).
  • EXPECTED: amber "Needs review" with the do-not-recharge warning → press Check again → resolves to approved. Never re-charges.

T-9.6 Kill the server — approved mid-flight — local-only, PASSED 27-Jul

  • Cannot be run against Vercel (serverless — nothing to Ctrl-C). Already evidenced locally: recovery.start → reconcile.resolved, txn approved, no double charge. Keep the 27-Jul logs as the evidence for this class.

T-9.7 Kill the server — txn never happened — local-only, PASSED 27-Jul

  • Same — not runnable on Vercel. Evidence: 27-Jul local run (reconcile.not_found_failed, no charge). On Vercel the equivalent safety is the per-request auto-reconcile on every status poll.

T-9.8 Browser dies after approval

  • WEBSITE: start a purchase; after the approval shows but before pressing Done, close the browser tab. Reopen.
  • VPP: CARD STEPS (a normal approval — the failure is on the browser side).
  • EXPECTED (known limitation): charge exists in linkly_transactions (approved) but no sale payment. Find it: SELECT txn_ref,status,amount_cents FROM linkly_transactions ORDER BY created_at DESC LIMIT 5; → record the payment manually. (Admin journal UI is a deferred build.)
